# Source Pack — AI Engineering / Agent Systems

Use this pack when `/radar` or `/wedge` evaluates AI engineering, agent systems, LLM infrastructure, evaluation, reliability or developer-tool opportunities.

## Demand signals

Prioritize first-party evidence:

1. Job descriptions from model labs, AI infrastructure companies, agent startups and AI-native product teams.
2. Engineering posts describing production problems: evaluation, latency, tool reliability, observability, context limits, memory, cost and data quality.
3. Product/API launches that create new implementation work rather than only model hype.
4. GitHub repositories with sustained contributor growth, issue activity and downstream integrations.
5. Repeated customer pain reported by infrastructure vendors or implementation teams.

## Useful capability clusters

- Agent evaluation and reliability
- Context engineering and memory
- Tool-use / browser / computer-use reliability
- Observability and tracing
- Inference cost / latency optimization
- Data pipelines for post-training and evaluation
- Voice / realtime agent infrastructure
- Security and permissioning for agents
- Harness / orchestration engineering

## Saturation checks

Downgrade directions when:

- a polished demo can be reproduced from a one-hour tutorial;
- the project is mainly a UI around a commodity API;
- candidates can claim the skill without showing measurable artifacts;
- the JD treats the skill as generic baseline knowledge rather than a differentiator.

## High-value proof

Prefer:

- fixed-task benchmark with raw results;
- failure taxonomy;
- ablation or baseline comparison;
- reliability / cost / latency measurement;
- merged contribution to a relevant OSS project;
- production-like integration with explicit constraints;
- user or operator feedback.

## Example wedge questions

- Which part of agent deployment is moving from demo problem to production budget?
- Which reliability failure appears repeatedly across different teams?
- Which capability is easy to claim but hard to prove?
- Can a 72-hour benchmark expose meaningful variation between approaches?
